状态：测试边界已由用户确认；正式规格见 [codex-unfence 三命令使用体验与项目改名](https://github.com/pzehrel/codex-browser-liberation-patch/issues/27)，后续规格变更以该 issue 为准。需求来自本轮已确认的产品决策；已有工作区实现仅作为待验收候选，不反向决定需求。

## Problem Statement

用户希望通过一条命令安装 Codex 浏览器补丁、一条命令同时检查能否安装和当前状态、一条命令卸载。已有入口要求用户理解交互动作、应用与恢复术语以及本地打包步骤，README 未能清楚表达这三个直接动作。

项目还使用较长且不一致的项目名、npm 包名和可执行名称。用户已决定统一改名为 codex-unfence。

## Solution

以 codex-unfence 为统一项目、npm 包及 CLI 名称。公共 npm 发布后的普通使用入口为：

- `npx codex-unfence install`：发现安装、检查条件、必要时选择目标，确认后安装插件文件补丁。
- `npx codex-unfence check`：只读汇总全部发现的安装，分别报告结构兼容性、当前补丁状态、能否安装及阻断原因。
- `npx codex-unfence uninstall`：必要时选择目标，确认后撤销补丁并恢复原始文件。

“一条命令”允许必要交互，不意味着静默写入。单一安装自动选中；多安装写操作由用户选择。安装和卸载遇到未完成事务时，在同一次命令中引导用户确认回滚，重新检查后，再确认继续原请求，普通用户无需学习独立恢复命令。

当前包尚未公共发布，公共 npx 命令是交付目标。发布前使用本地安装包验证同一可执行入口，不将需要克隆与构建的开发路径作为普通用户最终使用流程。

## User Stories

1. 作为首次使用者，我希望通过一条 npx 命令安装补丁，以便无需克隆仓库、构建源码或全局安装工具。
2. 作为使用者，我希望项目名、包名与 CLI 名称都是 codex-unfence，以便记住并识别同一个工具。
3. 作为使用者，我希望通过一条命令同时检查兼容性和补丁状态，以便无需分别运行检测和状态查询。
4. 作为拥有多个安装的使用者，我希望检查命令列出全部安装，以便一次了解各安装情况。
5. 作为使用者，我希望诊断明确归属于对应安装，以便知道哪个安装存在什么问题。
6. 作为使用者，我希望看到能否安装及阻断原因，以便区分代码不受支持、应用仍运行、权限不足和恢复资料冲突。
7. 作为谨慎的使用者，我希望检查只读且不要求交互确认，以便查看状态时不生成备份或修改安装。
8. 作为使用者，我希望工具自动发现常见位置的应用，以便无需定位内部服务文件。
9. 作为使用者，我希望显式提供应用绝对路径，以便检查或操作其他位置的安装。
10. 作为只有一个安装的使用者，我希望工具自动选中目标，以便减少无意义选择。
11. 作为拥有多个安装的使用者，我希望写入前主动选择目标，以便避免修改错误安装。
12. 作为使用者，我希望安装或卸载前看到准确目标、修改范围及签名影响，以便作出明确确认。
13. 作为使用者，我希望只有输入 yes 才执行写操作，以便取消、其他输入或 EOF 不会自动授权修改。
14. 作为使用者，我希望工具提示我自行退出和重新打开应用，以便掌握正在运行的工作。
15. 作为使用者，我希望相关进程仍运行或无法核实时阻止写入，以便不会把未知进程状态当作已退出。
16. 作为使用者，我希望重复安装已存在的补丁保持幂等，以便不必先记住当前状态。
17. 作为使用者，我希望通过一条卸载命令恢复原始文件，以便不必了解准备目录和事务存储。
18. 作为使用者，我希望重复卸载以及对已确认原版的卸载不重复改写文件，以便放心重试。
19. 作为经历操作中断的使用者，我希望下次安装或卸载自动识别未完成操作，以便无需另学恢复入口。
20. 作为经历操作中断的使用者，我希望工具解释回滚将恢复到操作前状态，以便不会把回滚误认为完成上次操作。
21. 作为使用者，我希望回滚和后续安装或卸载分别确认，以便确认恢复不等于授权后续修改。
22. 作为使用者，我希望恢复失败或未知文件变化时停止并保留现场，以便不会覆盖无法核实的内容。
23. 作为回滚后取消后续动作的使用者，我希望看到准确的当前状态和取消说明，以便不会误认为本次命令完全没有修改文件。
24. 作为使用者，我希望恢复资料独立于 npm 缓存，以便清理临时代码后仍可通过匹配版本的工具卸载或恢复。
25. 作为旧工具使用者，我希望明确知道新工具不接管旧记录，以便先使用原工具处理旧补丁。
26. 作为更新应用的使用者，我希望得到先卸载、更新后重新检查的指引，以便不使用旧备份覆盖新版文件。
27. 作为使用者，我希望区分结构支持、磁盘补丁状态和运行生效，以便不会把文件写入成功当作网站访问已验证。
28. 作为自动化检查调用者，我希望检查命令提供结构化输出和明确失败码，以便识别参数错误、不兼容、冲突与运行失败。
29. 作为阅读 README 的使用者，我希望首先看到三个常用命令，以便快速完成操作，开发和高级入口放在后面。
30. 作为维护者，我希望通过可分发的本地安装包验证普通使用流程，以便发布前确认真实 npx 入口可用。

## Implementation Decisions

- 复用现有安装发现、结构分析、补丁变换和事务恢复能力；本轮改变命令体验与产品身份，不扩大站点状态响应改写范围。
- install 和 uninstall 分别表达安装与撤销插件文件补丁；它们不表示全局安装或移除 npm 工具。
- 自动发现保持 macOS 常用应用目录范围；显式应用路径用于缩小检查范围或指定非默认位置的目标。不能依据版本大小或应用名称猜测写入目标。
- check 对全部候选逐项检查，不因需要写入选择而拒绝只读汇总；单个目标失败不能隐藏其他目标结果。结构支持、文件状态、写入条件与运行验证分别表达，诊断须可定位到对应安装。
- 检查命令保留 JSON 输出及明确退出码：成功为 0，运行失败为 1，参数错误为 2，不兼容为 3，冲突为 4。混合安装结果按运行失败、冲突、不兼容、成功聚合。进程阻断等写入条件在结果中独立报告，不能将检查完成等同于可以写入。
- 普通写入口要求真实输入、输出终端和明确确认，拒绝 JSON 自动写入。npx 自身的包获取确认与工具的文件修改确认相互独立。
- 未完成事务先回滚到该事务实际开始前的状态；回滚成功后重新检查并重新确认当前请求。回滚失败、内容冲突或身份变化时停止，不继续写入。回滚后的取消提示必须承认已发生的恢复操作。
- 显式请求因不兼容、冲突或运行失败无法执行时，应报告原因与非零退出码；不能把检查拒绝写入报告为操作成功。用户主动拒绝尚未发生的写入可以作为正常取消。
- 安装和卸载保持幂等。对于当前受支持且已确认的原始文件，卸载可直接报告未安装，不要求先创建补丁备份。
- 新产品使用独立的 codex-unfence 恢复资料与协调命名空间。不读取、识别或迁移旧产品名的恢复记录，也不删除旧资料；旧补丁需要原工具处理。无法确认来源的已修改文件不能当作可信原版或新工具补丁。
- 保留私有备份、可信记录、目标身份校验、进程检查与事务门禁；项目改名不放宽写入条件，也不修改既有结构兼容性与依赖假设。
- README、包元数据、公开命令帮助及恢复版本提示与统一名称保持一致。历史证据和既有工作项保留当时身份及链接。
- GitHub 仓库目标名称同为 codex-unfence。实际仓库改名和公共 npm 发布属于实现验证后的外部交付步骤，不能用本地改名或离线测试冒称已完成。
- 现有高级入口的去留不是三命令体验的验收前提；普通用户不得依赖它们完成安装、检查、卸载及中断处理。

## Testing Decisions

- 主要验收边界采用已有的“本地打包产物经真实 npx 启动公开 CLI”。观察用户可见输出、退出码、目标文件内容与恢复资料变化，不断言内部 AST 节点、私有函数或实现顺序。
- 在合成应用和隔离临时文件系统中运行；交互行为使用真实伪终端驱动输入。保留现有进程、文件系统与账户边界夹具，不访问或修改真实安装，不发出真实业务请求。
- 复用现有打包执行、托管 CLI、事务生命周期及中断注入回归作为先例。默认发现、JSON 和人类输出的快速反馈可以复用源码 CLI 测试辅助入口，但不能替代最终打包入口验收。
- 覆盖单一与多个安装、混合兼容性、显式路径、无安装、全部安装诊断归属、只读检查不创建恢复资料、命令帮助及参数错误。
- 覆盖安装、卸载、重复操作、未安装时卸载、真实终端要求、精确确认、拒绝与 EOF，以及进程或权限阻断后的正确退出状态。
- 覆盖安装和卸载中断，拒绝回滚、回滚后继续、回滚后取消、再次中断及冲突拒绝；以实际文件状态证明结果，不只匹配成功文本。
- 覆盖 npm 缓存移除后的重新获取与恢复，以及新命名空间不读取、不改动旧恢复资料。
- 覆盖包名、可执行名称、打包清单和运行依赖一致性。离线打包测试不能证明公共 registry 已可获取，公共发布后的一行命令验证作为独立交付证据。
- 最终候选通过明确基线的仓库统一检查，包含空白、类型、lint、构建和测试；审查后发生修改需按影响复验。真实应用加载、签名和网站访问另行报告，不从合成测试推断。

## Out of Scope

- 新增其他平台支持、任意版本兼容承诺、扩大结构模式或重写补丁分析器。
- 修改用户授权、企业策略、网站登录和网站自身访问限制。
- 自动结束、启动应用，提权、重新签名或关闭系统验证。
- 读取、迁移、删除旧产品恢复记录，或让新工具接管旧工具补丁。
- 在本规格编写阶段执行真实安装修改、真实网站访问、公共 npm 发布或 GitHub 仓库改名。
- 以重构所有高级旧入口为本轮交付条件。
